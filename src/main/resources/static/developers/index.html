Engineering highlights

This project was designed to be production-style: clear API contracts, input validation, and an interface that stays stable across multiple clients.

🏗️

Clean architecture

Controller → service → persistence layering with DTO-based responses for predictable API output.

Designed so new modes/maps can be added without breaking clients.

🔐

Secure submissions

Score submission requires a short-lived session token and a validated request body.

Reduces abuse without forcing account creation.

⚡

Performance & UX

Paginated leaderboard reads with fast filtering options on the client UI.

Same endpoint serves both desktop and web.

API reference

Endpoints consumed by the desktop client and the web UI.

GET /api/leaderboard

Fetch leaderboard entries filtered by mapId, mode, and optional difficulty.

Query
mapId, mode, difficulty (optional), limit, offset 
GET /api/leaderboard?mapId=0&mode=STANDARD&limit=25&offset=0
Web behavior
The website filter logic matches the desktop client (mode controls map behavior; “ANY” difficulty is not sent).
POST /api/session

Start a short-lived session used to authenticate score submissions. 

POST /api/session
Headers for submit
Use X-Session-Id and X-Session-Token returned by this endpoint.
POST /api/scores

Submit a score. Requires session headers and validated JSON request body. 

POST /api/scores
X-Session-Id: <uuid>
X-Session-Token: <token>
Validation
Player name pattern + bounds checks keep data clean and reduce abuse.
GET /health

Health check endpoint for uptime monitoring and deploy verification.

GET /health
